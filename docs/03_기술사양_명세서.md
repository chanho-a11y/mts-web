## 1. 아키텍처 개요

### 1.1 시스템 컨텍스트

```
  normcorecoffee.com (B2C)─┐
  mtspace.coffee     (B2B)─┤   ← 2개 도메인이 같은 앱으로 라우팅
                ┌──────────▼──────────────────────────────────┐
   고객(B2C)────▶│   Next.js (App Router) — Vercel             │
   사업자(B2B)──▶│   - 미들웨어: Host→storefront(브랜드/테마)    │
   관리자───────▶│   - Storefront ×2 (SSR/SSG/ISR)             │
                │   - /admin (통합 관리자)                     │
                │   - Route Handlers / Server Actions (API)   │
                │   - resolve_price(회원·브랜드 맥락)          │
                │   - 자산 생성 서비스(템플릿→래스터/텍스트)    │
                └───────┬───────────────┬───────────┬─────────┘
                        │               │           │
                        ▼               ▼           ▼
                ┌───────────────┐ ┌──────────────┐ ┌──────────────┐
                │ Supabase      │ │ 멀티 PG       │ │ 외부 서비스   │
                │ - Postgres    │ │ - 이니시스     │ │ - 이메일      │
                │ - Auth        │ │ - 카카오페이   │ │ - 택배/송장   │
                │ - Storage     │ │ - 페이팔(외화) │ │ - 세금계산서  │
                │   (자산버킷)   │ │ 승인/환불     │ │ - GA4/Pixel  │
                │ - RLS         │ └──────────────┘ │ - 네이버 동기화│
                │ - Edge Func   │   provider 어댑터  │ - (LLM 초안)  │
                └───────────────┘                   └──────────────┘
   자산 생성 서비스 ─렌더─▶ Satori/@vercel/og(이미지) · Playwright(복합) · 공유 React 템플릿
                    └─텍스트─▶ 상세/블로그 네이티브 + (선택)LLM 초안 → 검수 → 발행
```

### 1.2 핵심 설계 원칙
- **서버 우선 렌더링**: 상품·컬렉션·블로그는 SSG/ISR, 개인화·장바구니·체크아웃은 SSR/CSR 혼합. SEO·AIEO 동기 충족.
- **신뢰 경계는 서버**: 가격/재고/할인/결제 검증은 Server Action·Route Handler·DB 함수에서. 클라이언트 값 불신.
- **RLS로 데이터 격리**: B2C/B2B/관리자 권한을 Postgres RLS로 강제. 클라이언트 숨김에 의존하지 않음.
- **멱등성**: 결제 콜백·재고 차감·주문 처리는 중복 호출에 안전.
- **단일 소스**: 자사몰 DB가 카탈로그·재고·가격의 마스터. 채널 동기화는 단방향(자사몰→외부) 우선.
- **멀티 스토어프론트**: 한 앱·한 DB가 2개 도메인을 운영. 공유(상품·재고·SKU·주문·결제·회원) vs 분기(노출·가격·디자인·언어)를 명확히 구분.
- **가격은 맥락 함수**: 가격은 상수가 아니라 `f(variant, 회원, 브랜드)`. 단일 해석 경로(`resolve_price`)로만 산출.

### 1.2.1 멀티 스토어프론트 모델 (v1.1)

| 구분 | 공유(Shared, 단일 마스터) | 분기(Per-storefront) |
|------|--------------------------|----------------------|
| 데이터 | 상품·SKU·재고·주문·결제·회원·쿠폰 | 브랜드 노출 플래그·테마·홈/콘텐츠·언어·발신메일·SNS |
| 코드 | 커머스 로직·DB·결제·관리자 | 레이아웃·디자인토큰·카피·브랜드 컴포넌트 |
| 운영 | 통합 관리자·통합 재고·통합 정산(태그 구분) | 브랜드별 마케팅·SEO·도메인 |

- **도메인 매핑**: `normcorecoffee.com → storefront=normcore(B2C 기본)`, `mtspace.coffee → storefront=mtspace(B2B 기본)`.
- 같은 법인이므로 **PG 계약(이니시스·카카오페이·페이팔)·세금·정책은 공통**. 결제 영수증·발신자 표기만 브랜드별 분기.
- 구현 방식: **단일 Next.js 앱 + Host 기반 미들웨어 분기**(권장, 코드·세션 공유 용이). 멀티존/별도배포는 비채택(공유 복잡도↑).

## 2. 데이터 모델 (Supabase Postgres)

> 표기는 개념 스키마. 실제 마이그레이션은 `supabase/migrations/`에 SQL로 관리. 금액은 **정수(원)**, 시간은 `timestamptz`(KST 표시), 식별자는 `uuid` 기본.

### 2.1 ERD 개요

```
brand (MTSPACE / NORMCORE) ─1:N─ storefront (도메인) 
storefront ─maps─ domain (Host)

profiles ─1:1─ auth.users
profiles ─1:N─ addresses
profiles ─1:1─ business_accounts (B2B, 사업자)
profiles ─N:1─ price_tier (등급)
profiles ─1:N─ customer_variant_prices ──▶ product_variant   ★회원 개별가
price_tier ─1:N─ variant_prices                              ★등급가

product ─1:N─ product_variant ─1:N─ variant_prices
product ─N:M─ storefront (product_storefronts)               ★브랜드 노출
product ─N:M─ category (product_categories)
product ─1:N─ product_image

cart ─(brand/storefront 태그)─1:N─ cart_item ──▶ product_variant
order ─(brand/storefront 태그)─1:N─ order_item ──▶ product_variant
order ─1:N─ payment ──▶ (PG 거래: inicis/kakaopay/paypal)
order ─1:N─ shipment

coupon ─N:M─ order (applied)
subscription ─1:N─ subscription_item   (P1)
review ──▶ product / profiles            (P1)
inventory_ledger ──▶ product_variant     (재고 이력, SKU 단위 공유)
content_post (blog/Coffeelog, storefront 태그)
faq (동적 FAQ, category·brand/storefront·연결 product, FAQPage)
contact_message (문의, storefront 태그)
newsletter_subscriber (storefront 태그)
audit_log

[가격 해석] resolve_price(variant, profile, storefront)
   = COALESCE(customer_variant_prices, variant_prices[tier], variant.base_price)
```

### 2.2 주요 테이블 (요약)

#### 브랜드/스토어프론트 (v1.1 신규)
- **brand**: `id`, `code`('mtspace'|'normcore'), `name`, `legal_entity`(공통: (주)엠티에스솔루션스), `logo`, `default_locale`, `default_audience`('b2c'|'b2b').
- **storefront**: `id`, `brand_id`, `domain`(유니크, 예: 'normcorecoffee.com'·'mtspace.coffee'), `theme`(jsonb 디자인토큰), `locale`, `default_customer_type`('b2c'|'b2b'), `sender_email`, `policy_overrides`(jsonb), `is_active`. (로컬 개발용 보조 도메인 허용)
- **product_storefronts**(N:M): `product_id`, `storefront_id`, `is_visible`, `position`. → 상품이 어느 도메인에 노출될지. 한 상품이 양쪽 노출 가능.

#### 사용자/계정
- **profiles**: `id(uuid, =auth.users.id)`, `email`, `name`, `phone`, `customer_type('b2c'|'b2b')`, `price_tier_id(null=일반)`, `marketing_opt_in`, `created_at`.
- **business_accounts**: `id`, `profile_id`, `company_name`, `biz_reg_no`(사업자번호), `representative`, `contact_name`, `contact_phone`, `biz_reg_file_path`(Storage, 비공개), `status('pending'|'approved'|'rejected')`, `approved_by`, `approved_at`, `tax_invoice_email`. 
- **addresses**: `id`, `profile_id`, `recipient`, `phone`, `zipcode`, `addr1`, `addr2`, `is_default`, `entrance_memo`.
- **price_tier**: `id`, `name`('일반','도매-기본','도매-VIP'…), `is_b2b`.

#### 카탈로그
- **product**: `id`, `slug`(URL, 유니크·보존), `title_ko`, `title_en`, `brand`('MTSPACE COFFEE'|'NORMCORE COFFEE'), `product_type`('블렌드'|'싱글오리진'|'디카페인'|...), `status('active'|'draft'|'archived')`, `is_b2b_only`(bool), `roast_level`, `flavor_notes`(text[]), `origin`(country/region/farm jsonb), `process`(가공), `brew_recommendation`(text[]), `body_html`(리치 콘텐츠), `featured_image_id`, `published_at`, `seo_title`, `seo_description`.
  - **원두 프로파일 확장(v1.2, 자산 생성용 단일 소스)**: `producer`(생산자), `variety`(품종), `altitude`(고도), `brew_recipe`(jsonb: espresso `{dose,yield,time}` / filter `{recipe,ratio,temp}`), `weight_g`, `packaging`(예: PET), `storage`(보관), `shelf_life`(유통기한), `ingredients`(원재료), `key_color`(제품 키컬러 HEX = 자산 `--brand` = **카드뉴스 SKU 시그널 컬러**, BRAND_TOKENS v2 24 SKU 실측값 시드), `palette`(jsonb 보조 색), `hashtags`(text[]), `maker_info`(판매자 표기). → 이 필드들이 라벨·카드뉴스·썸네일·상세·블로그의 입력원. (기존 디자인 스튜디오·인스타 카드뉴스 입력과 1:1, §14.2/§14.7)
  - 카드뉴스 자동주입(§14.7)은 추가 필드 없이 기존 데이터 재사용: 제목→`title_ko/en`, 농장명→`origin/producer`(farmName 추출), 가공→`process`, 풍미노트→`flavor_notes`, 설명→`body_html` 발췌.
- **product_variant**: `id`, `product_id`, `sku`(유니크·NOT NULL), `option_values`(jsonb, 예: {weight:'125g', grind:'whole'}), `weight_g`, `grind`('whole'|'espresso'|'drip'|...), `base_price`(정수원, 부가세포함), `barcode`, `is_active`, `inventory_policy('deny'|'continue'|'preorder')`, `inventory_qty`(현재고, ledger로 관리), `position`.
- **variant_prices**: `id`, `variant_id`, `price_tier_id`, `price`(정수). (도매가/등급가 — 그룹 단위)
- **customer_variant_prices** (v1.1 신규, ★회원 개별가): `id`, `profile_id`, `variant_id`, `price`(정수), `starts_at`, `ends_at`(null=무기한), `note`, `created_by`, `updated_at`. 유니크(profile_id, variant_id, 유효기간). → 특정 회원에게만 적용되는 계약 단가. `variant_prices`(등급)보다 우선.
- **category**: `id`, `slug`, `name`, `parent_id`(트리), `is_b2b`, `position`, `rule`(jsonb, 스마트컬렉션 규칙 선택).
- **product_categories**: `product_id`, `category_id`.
- **product_image**: `id`, `product_id`, `variant_id(null)`, `storage_path`, `alt`, `position`.
- **inventory_ledger**: `id`, `variant_id`, `delta`(+/-), `reason`('order'|'restock'|'adjust'|'return'), `ref_id`, `created_at`. → 현재고는 합으로 계산/캐시.

#### 장바구니/주문/결제
- **cart**: `id`, `profile_id(null=게스트)`, `session_token`, `updated_at`.
- **cart_item**: `id`, `cart_id`, `variant_id`, `qty`, `unit_price_snapshot`.
- **order**: `id`, `order_no`(사람용 유니크), `profile_id(null=게스트)`, `customer_type`, `brand_id`/`storefront_id`(★주문 발생 브랜드·도메인), `status`(아래 상태머신), `email`, `phone`, `shipping_address`(jsonb 스냅샷), `items_subtotal`, `discount_total`, `shipping_fee`, `grand_total`(부가세포함), `currency`('KRW' 기본, 페이팔 결제 시 외화), `tax_amount`(공급가/부가세 분해 보관), `coupon_id`, `note`, `placed_at`, `paid_at`, `channel`('web').
- **order_item**: `id`, `order_id`, `variant_id`, `sku`, `title_snapshot`, `option_snapshot`, `unit_price`, `price_source`('individual'|'tier'|'base', ★적용 단가 근거), `qty`, `line_total`.

### 2.3 주문 상태머신

```
created(미결제) 
   └─결제승인─▶ paid(결제완료)
                   └─준비─▶ preparing(로스팅/포장)
                               └─출고─▶ shipped ─▶ in_transit ─▶ delivered(완료)
created/paid ─취소─▶ cancelled
paid/preparing/delivered ─환불─▶ refunded / partial_refunded
```
- 상태 전이는 DB 함수/Server Action에서만. 각 전이는 `audit_log` + 재고 ledger 동반.
- `paid` 진입 시점에만 재고 차감(또는 정책에 따라 created 시 예약). 결정은 01 지침 "재고 정책" 확정 후.

### 2.4 RLS 정책 (요지)
- `profiles`, `addresses`, `cart`, `order`(본인): `auth.uid() = profile_id`만 read/write.
- `business_accounts`: 본인 read, 관리자 all. 파일은 Storage 비공개 + 서명 URL.
- `product`/`category`: 공개 read는 `status='active' AND is_b2b_only=false`. **도매 상품/도매가(variant_prices, is_b2b)** 는 `customer_type='b2b' AND business_accounts.status='approved'`인 경우만 노출.
- `variant_prices`: 일반 가격티어는 공개, 도매티어는 승인 B2B만.
- `customer_variant_prices`: 본인(`auth.uid()=profile_id`) read만, 쓰기는 관리자. 타인 개별가 접근 불가.
- `product_storefronts`: 공개 read. 단, 스토어프론트 필터는 쿼리에서 강제(현재 도메인에 `is_visible=true`인 상품만).
- `faq`: 공개 read는 `status='published' AND is_b2b_only=false`. 도매·세금계산서 FAQ(`is_b2b_only=true`)는 승인 B2B만. 스토어프론트 필터 적용.
- 관리자: 별도 `role='admin'`(profiles 또는 커스텀 claim) → 전체 접근. service_role 키는 서버 전용.

### 2.5 상품 노출(스토어프론트) 규칙
- 스토어프론트 목록/검색/사이트맵/JSON-LD는 항상 `product_storefronts.is_visible=true AND storefront_id=현재도메인 AND product.status='active'`로 필터.
- B2B 전용 상품은 추가로 `customer_type='b2b' AND business_accounts.status='approved'` 조건. (브랜드 노출 ∩ 권한 노출)
- normcore(B2C) 도메인에서는 도매 전용 상품·도매가가 절대 노출되지 않도록 쿼리·RLS 이중 차단.

### 2.6 가격 해석 (Price Resolution) — 회원별 차등가격 (v1.1)

가격은 단일 진입점으로만 계산한다. 애플리케이션 서비스 `resolvePrice()`와 동등한 SQL 함수를 둔다(목록 성능·정합).

```sql
-- 개념 예시 (정수 KRW, 부가세 포함가)
create or replace function resolve_price(
  p_variant_id uuid,
  p_profile_id uuid,        -- null = 비로그인
  p_at timestamptz default now()
) returns table(price int, source text) language sql stable as $$
  -- ① 회원 개별가
  select cvp.price, 'individual'
  from customer_variant_prices cvp
  where cvp.variant_id = p_variant_id
    and cvp.profile_id = p_profile_id
    and p_at >= cvp.starts_at
    and (cvp.ends_at is null or p_at < cvp.ends_at)
  order by cvp.starts_at desc
  limit 1
  union all
  -- ② 등급(티어)가  — ①이 없을 때만
  select vp.price, 'tier'
  from variant_prices vp
  join profiles pr on pr.id = p_profile_id
  where vp.variant_id = p_variant_id
    and vp.price_tier_id = pr.price_tier_id
    and not exists (
      select 1 from customer_variant_prices c
      where c.variant_id = p_variant_id and c.profile_id = p_profile_id
        and p_at >= c.starts_at and (c.ends_at is null or p_at < c.ends_at))
  limit 1
  union all
  -- ③ 기본 소비자가 — ①②가 모두 없을 때만
  select v.base_price, 'base'
  from product_variant v
  where v.id = p_variant_id
    and not exists (select 1 from customer_variant_prices c
        where c.variant_id=p_variant_id and c.profile_id=p_profile_id
          and p_at>=c.starts_at and (c.ends_at is null or p_at<c.ends_at))
    and not exists (select 1 from variant_prices vp join profiles pr on pr.id=p_profile_id
        where vp.variant_id=p_variant_id and vp.price_tier_id=pr.price_tier_id)
  limit 1;
$$;
```

- 목록 화면은 `resolve_price`를 활용한 **뷰 또는 lateral join**으로 N+1 없이 일괄 계산.
- 장바구니·견적·체크아웃·주문 항목은 계산된 `unit_price` + `price_source`를 **스냅샷 저장**(추후 단가 변경에 영향받지 않음).
- 결제 직전 서버가 **재계산하여 합계 검증**(클라이언트 값 불신, 02 skills 규칙 3-2).
- 관리자: 회원별 단가표 CRUD + (P1) 엑셀 임포트. 모든 변경 `audit_log`.

## 4. 결제 연동 (멀티 PG: 이니시스 · 카카오페이 · 페이팔)

> **두 도메인 / 멀티 PG(v1.4)**: 동일 법인((주)엠티에스솔루션스)이라 PG 계약은 공통이고 양 도메인이 공용. 결제 콜백 URL은 요청 도메인 기준 동적 생성, 영수증·발신메일·상호 표기만 브랜드별 분기. 주문의 `brand_id`로 브랜드별 매출 구분 집계.

### 4.0 provider 어댑터 (멀티 PG 추상화)
- 주문/결제 모델은 **PG 중립**. `payment.provider`('inicis'|'kakaopay'|'paypal')에 따라 어댑터가 결제창 호출·승인·검증·취소의 차이를 캡슐화.
- 공통 계약: `init(order)→결제수단별 시작 파라미터`, `approve(callback)→검증 후 paid`, `cancel(payment, amount)→취소/환불`. 멱등성·금액·통화 검증은 공통 레이어에서 강제.
- 통화: 이니시스·카카오페이=KRW, 페이팔=외화(USD 등). 주문 `currency` 기록, 금액 검증은 통화 단위로.
- 결제수단별 적용 범위(브랜드·B2B/B2C)는 설정값으로 분기(예: B2B 도매=이니시스+세금계산서 중심). — 01 §9 결정.

### 4.1 이니시스 (INIStdPay) — 국내 표준결제창

```
1) 주문 생성: order(status=created, grand_total 확정) + payment(status=ready, idempotency_key)
2) 결제 파라미터 생성(서버): mid, oid(=order_no), price, timestamp, signature(SHA256), returnUrl, closeUrl
3) 결제창 호출(클라이언트): INIStdPay.pay(form)  → 카드/계좌이체/가상계좌/간편결제
4) 인증 결과 수신: POST returnUrl (authToken, authUrl, netCancelUrl, mid, orderNumber ...)
5) 승인 요청(서버→authUrl): 서버에서 승인 API 호출
6) 검증: 응답 금액 == order.grand_total, oid 일치, 서명/해시 검증
7) 성공: payment.status=paid, order.status=paid, paid_at, 재고 ledger 차감, 주문확인 메일
   실패: payment.status=failed, 사용자 안내
   망취소(승인 후 우리측 오류): netCancelUrl로 망취소 호출하여 정합성 보장
8) 가상계좌: 입금 전 'ready', 입금 통지(noti)에서 paid 전이
```

### 4.2 이니시스 구현 주의사항
- **서명/해시**: 이니시스 매뉴얼의 SHA256 서명 규칙을 정확히. signKey는 서버 환경변수.
- **금액 검증 필수**: 승인 응답의 결제금액과 주문금액 불일치 시 즉시 망취소/실패 처리.
- **멱등성**: `idempotency_key`(oid+tid) unique. 콜백 중복 수신에도 1회만 paid 처리(상태 가드 + 트랜잭션).
- **부분취소/환불**: 취소 API에 잔액·부분금액 지원. refund 테이블로 추적, 재고 환입(return) 여부 정책화.
- **결제수단**: 카드, 계좌이체, 가상계좌(입금기한·노티). (카카오페이는 §4.3에서 별도/또는 이니시스 경유 — 01 §9 결정)
- **현금영수증**: 이니시스 발급 옵션 활용 또는 별도. B2B는 세금계산서로 분리.
- **테스트→운영**: 테스트 MID로 전 시나리오 QA 후, 운영 MID·signKey 전환은 사용자 확인 하에.
- **PCI/보안**: 카드정보 우리 서버 미경유(결제창 위임). 우리 DB엔 tid·상태·마스킹 정보만.

### 4.3 카카오페이 — 간편결제
- 연동 경로 2택(01 §9 결정): **(a) 이니시스 경유** 간편결제 옵션(별도 계약 불필요, 이니시스 플로우 재사용) vs **(b) 카카오페이 직접 연동**(별도 가맹·API).
- 직접 연동 플로우: `ready`(서버, tid 발급) → 사용자 카카오 인증(리다이렉트/팝업) → `approve`(서버, `pg_token`) → 검증 → paid. 취소 API로 환불·부분취소.
- 멱등성·금액 검증은 공통 레이어. KRW 전용.

### 4.4 페이팔 — 해외/외화
- 플로우: Orders v2 `create`(서버, 통화·금액) → 사용자 승인(페이팔 결제창) → `capture`(서버) → 검증 → paid. 웹훅으로 분쟁·환불 상태 동기화.
- **통화**: USD 등 외화. 주문 `currency`·환율 정책 필요. 국내 부가세·현금영수증과 별개 처리.
- **해외배송·관세·반품**: 글로벌 주문이면 배송비·관세·반품 정책 별도(01 §2.8 비목표 경계, §9 결정). 초기엔 페이팔을 특정 국가/품목에 한정 가능.
- 분쟁(Dispute/Chargeback) 대응 프로세스 정의.

### 4.5 공통 주의
- 모든 PG: 실패/취소/타임아웃/중복콜백/부분환불 시나리오 QA. 각 PG 샌드박스로 검증 후 운영 전환(사용자 확인).
- 결제정보(카드·계좌)는 어느 PG도 우리 DB에 저장하지 않음. tid·상태·통화·마스킹만.

> 참고: 멀티 PG 직접 연동 부담을 줄이려면 **포트원(PortOne) 등 결제 오케스트레이션**으로 이니시스·카카오페이·(일부)페이팔을 단일 API로 묶는 방식도 가능(계약 PG 유지, 연동·웹훅·환불 표준화). 직접 연동 대비 공수 절감 트레이드오프 — 01 §9 결정.

## 5. 인증·권한

- **Supabase Auth**: 이메일/비밀번호 + 소셜(구글) + **카카오 로그인 권장**(국내 전환율). 
- **통합 계정(v1.1, 권장)**: 한 Supabase Auth로 두 도메인 공통 로그인. 단, 도메인이 다르면(normcorecoffee.com vs mtspace.coffee) 세션 쿠키가 자동 공유되지 않으므로 **공용 auth 콜백/SSO 브리지(공통 서브도메인 또는 토큰 교환)** 로 도메인 간 로그인 연속성을 설계. (도메인별 분리 계정도 가능 — 01 §9 결정)
- **세션**: Next.js 미들웨어로 보호 라우트(`/account`, `/wholesale/catalog`, `/admin`) + 스토어프론트 컨텍스트 결정.
- **역할**: `b2c`(기본), `b2b`(승인), `admin`. RLS + 라우트 가드 이중.
- **마이그레이션 사용자**: 비밀번호 이전 불가 → 최초 로그인 시 재설정 메일.

## 6. SEO / AIEO 기술 사양

### 6.1 SEO
- 전 페이지 메타·canonical·OG·Twitter 카드(현 사이트 수준 이상).
- **스토어프론트별 SEO(v1.1)**: 각 도메인은 자신의 노출 상품만 담은 `sitemap.xml`·`robots.txt`·canonical(자기 도메인)·OG를 생성. 양 도메인에 같은 상품이 노출될 때 **중복 콘텐츠**가 되지 않도록 각 도메인 canonical은 자기 자신을 가리키되, 브랜드별 카피·메타를 차별화(동일 본문 복붙 지양). 필요 시 한쪽을 canonical 기준으로.
- `sitemap.xml`(상품/컬렉션/블로그/정적), `robots.txt` — 도메인별 분리.
- **301 리다이렉트 매핑표**: 기존 Shopify URL → 신 URL. 단, 슬러그 보존으로 가능한 한 동일 경로 유지.
- 이미지: `next/image`, 적절한 사이즈·lazy·alt(한국어). Core Web Vitals 예산(LCP<2.5s, CLS<0.1, INP<200ms).
- 한국어/영어 병기 콘텐츠는 hreflang/언어 표기 정리(국내 우선, 글로벌 후속).

### 6.2 구조화 데이터(JSON-LD)
- `Organization`(회사·로고·SNS·연락처), `WebSite`(SearchAction).
- `Product` + `Offer`(가격·통화 KRW·재고상태) + (`AggregateRating` 리뷰 도입 후).
- `BreadcrumbList`, `Article`(블로그), `FAQPage`(**동적 FAQ에서 자동 생성** — 상품·정책·배송 FAQ, §15).

### 6.3 AIEO (AI 검색 최적화)
- `llms.txt`: 브랜드 개요·제품군·정책 요약을 AI가 읽기 쉬운 텍스트로.
- 제품 **사실표를 텍스트로**(풍미·로스팅·중량·산지·가공·추출) — 이미지 속 정보 금지(현 사이트는 상세정보가 이미지에 묻혀 있어 AI/검색 약점 → 개선 포인트).
- 자연어 FAQ, 명확한 제목 구조(H1/H2), 일관된 용어.

## 7. 데이터 마이그레이션 계획

### 7.1 단계
0. **브랜드 매핑**: 상품을 브랜드 노출(normcore/mtspace/양쪽)로 분류. 도매 전용은 mtspace(B2B), 소비자 소포장은 normcore(B2C) 기본, 공통 품목은 양쪽 + 가격 분기. normcorecoffee.com(GoDaddy) 본문·이미지는 브랜드 콘텐츠로 별도 수집.
1. **추출**: Shopify Admin(MCP/CSV)로 상품·변형·이미지·컬렉션·고객·주문·블로그 추출.
2. **변환**: 스키마 매핑 + 정규화. 풍미/로스팅/산지 등 본문→구조화 필드. **SKU 신규 부여**.
3. **적재**: 멱등 스크립트로 Supabase 적재(재실행 안전). 이미지 Storage 업로드.
4. **검증**: 건수·금액·이미지·URL 대조표. 샘플 수동 확인.
5. **301 매핑**: URL 매핑표 적용·테스트.

### 7.2 매핑 규칙(요지)
- product_type/태그 → category + product 속성.
- variant.sku 공란 → 규칙 생성(예: `MTS-DG-125-WB`).
- 음수 재고 → 0 또는 정책에 맞게(예약/품절) 보정.
- 고객 비밀번호 제외, 마케팅 동의 상태 이전.
- 주문 이력 → 참조 보관(신규 상태머신 미적용).

### 7.3 컷오버
- 스테이징 전체 QA → 소프트 런칭(서브도메인/소수 트래픽) → DNS 전환(mtspace.coffee) → Shopify 결제 종료/구독 해지. 병행 기간 동안 주문 일원화 룰 운영.

## 14. 디자인 스튜디오 통합 / 자산 자동생성 (v1.2)

기존 `MTSPACE_DESIGN_STUDIO.html`(단일 HTML, html2canvas+jsPDF+JSZip+PDF.js)의 템플릿·브랜드 토큰·생성 로직을 자사몰 관리자에 내장한다. **상품 레코드를 단일 입력원**으로, 제품 등록 시 5종 자산을 자동 생성한다.

### 14.1 데이터 흐름

```
[관리자] 상품 등록/수정  ── product(원두 프로파일 + key_color, §2.2 확장) ── 단일 소스
        │
        └─▶ generation_job(types=[detail,blog,label,cardnews,thumbnail], status=queued)
              │
   ┌──────────┴───────────────────────────────────────────────┐
   │                                                            │
   ▼ 텍스트 자산(네이티브, SEO/AIEO)              ▼ 이미지 자산(래스터, 인쇄/SNS/외부)
   ├─ content_draft: detail  (상품 데이터→구조화 상세)     ├─ 라벨 1300×1000  (인쇄/PDF)
   │     → 검수 → 상품 상세 HTML 렌더 + JSON-LD            ├─ 카드뉴스 [모드 토글] (§14.7)
   │                                                         │    · 단순 1080×1080
   └─ content_draft: blog   (제품+KB→초안+키워드, 선택 LLM) │    · 인스타 서사 1080×1350 (5장·15레이아웃)
                                                             └─ 썸네일 1080×1080 (목록/외부)
         → 사실검증 → Coffeelog 발행                          → 공유 React 템플릿 → 서버 렌더(Satori/Playwright)
   │                                                            │
   └──────────────┬─────────────────────────────────────────────┘
                  ▼
        product_asset / content_draft (Supabase Storage·DB, 버전·상태)
                  ▼
        [관리자] 검수·승인 게이트 ──▶ 발행 (자사몰 노출 / 채널 피드: 네이버·인스타)
```

핵심 원칙: **텍스트(상세·블로그)는 이미지로 굽지 않고 네이티브 렌더**(검색·AI가 읽음). **라벨·카드뉴스·썸네일만 이미지**(인쇄·SNS·외부채널). 자동 생성물은 **검수 후 발행**.

### 14.2 입력 매핑 (기존 스튜디오 → 상품 필드)

| 스튜디오 입력 | 상품 필드(§2.2) | 쓰이는 자산 |
|---|---|---|
| 제품명(한/영) | title_ko / title_en | 전부 |
| 산지·지역·농장·생산자 | origin(jsonb) / producer | 라벨·상세·블로그·카드뉴스 |
| 품종·가공·고도 | variety / process / altitude | 라벨·상세·블로그 |
| 로스팅 레벨 | roast_level | 전부 |
| 풍미노트 | flavor_notes[] | 전부 |
| 추출 레시피(에스프레소/필터) | brew_recipe(jsonb) | 상세·카드뉴스 |
| 중량·포장·보관·유통기한·원재료 | weight_g/packaging/storage/shelf_life/ingredients | 라벨(식품표시)·상세 |
| 키 컬러/팔레트 | key_color / palette | 전부(브랜드 토큰 `--brand`) |
| 해시태그 | hashtags[] | 카드뉴스·블로그·SNS |
| 판매자 정보 | maker_info | 라벨·상세(법적 표기) |

### 14.3 자산/콘텐츠 데이터 모델 (신규 테이블)

- **asset_template**: `id`, `type('label'|'cardnews'|'thumbnail'|'detail'|'blog')`, `brand_id`, `version`, `spec`(jsonb: canvas size·scale·page수·**모드·역할·레이아웃**), `component_ref`(렌더 컴포넌트 식별), `is_active`. (스튜디오 캔버스 스펙: label 1300×1000@3×, thumbnail 1080×1080@2×, detail 860×가변@3×)
  - **카드뉴스 spec(v1.3)**: `mode('simple'|'narrative')`, `ratio('4-5'|'1-1')`(simple=1080×1080, narrative=1080×1350), `roles`(narrative=`[hook,context,detail,experience,cta]`), `layouts_per_role`(A/B/C), `fill_markers`(data-fill/data-tn 매핑), `font`(--fs-head/--fs-body 기본 0.8/0.7, brand chrome 고정 0.7), `signal_color_source`('product.key_color'). 인스타 엔진(§14.7) 계승.
- **product_asset**: `id`, `product_id`, `variant_id(null)`, `type`, `storefront_id(null=공통)`, `storage_path`, `format('png'|'jpg'|'pdf'|'zip')`, `width`, `height`, `status('draft'|'generating'|'ready'|'failed'|'published')`, `source('auto'|'manual')`, `template_id`/`template_version`, `checksum`, `generated_at`, `published_at`.
- **content_draft**: `id`, `product_id`, `type('detail'|'blog')`, `brand_id`/`storefront_id`, `title`, `body_md`/`body_html`, `keywords`(text[]), `seo_title`/`seo_description`, `status('draft'|'review'|'published')`, `generator('template'|'llm')`/`model`, `fact_check`(jsonb: KB 대조 결과), `edited_by`, `published_at`. → 발행 시 상품 상세/`content_post`로 연결.
- **generation_job**: `id`, `product_id`, `requested_types`(text[]), `status('queued'|'running'|'done'|'failed')`, `result`(jsonb: 생성된 asset/draft id), `logs`, `error`, `requested_by`, `started_at`, `finished_at`. (멱등: product_id+types+상품 updated_at 기준 재실행 안전)
- **kb_entry**(지식베이스): `id`, `term`, `tier`, `context`, `definition`, `source`, `is_active`. → 블로그/상세 생성·사실검증의 근거(기존 스튜디오 KB 계승).
- **keyword**(키워드 사전): `id`, `term`, `group`, `intent`, `locale`. → 블로그·SEO·AIEO 키워드.

### 14.4 렌더링 아키텍처

**공유 템플릿** — 자산 템플릿을 **React 컴포넌트**로 작성해 두 용도로 재사용:
1. **온사이트 네이티브 렌더**(상세·블로그): 그대로 서버 컴포넌트로 HTML 출력 → 검색·AI 친화.
2. **이미지 래스터화**(라벨·카드뉴스·썸네일): 같은(또는 대응) 컴포넌트를 이미지로 변환.

**이미지 생성 방식(권장 조합)**
- **Satori + @vercel/og** — 썸네일·카드뉴스 등 정형 레이아웃: JSX→SVG→PNG. 빠르고 서버리스 친화, 무인 배치 적합.
- **Playwright(헤드리스 Chromium)** — 라벨·상세 등 복잡 레이아웃·다중 페이지·정밀 인쇄(PDF): 픽셀 정확. Vercel Functions(또는 별도 렌더 워커/컨테이너)에서 실행.
- **html2canvas(관리자 브라우저)** — 기존 스튜디오 파이프라인을 **수동 모드 폴백**으로 유지(현장에서 즉시 미세조정).
- 선택은 01 §9 의사결정(자산 생성 방식)에 따름.

**비동기 처리**: 생성은 `generation_job` 큐로 백그라운드 실행(Vercel Cron/Background Functions 또는 Supabase Edge Function + 큐 테이블). 등록 즉시 자동 또는 버튼 트리거(01 §9).

**Storage**: 비공개/공개 버킷 분리. 발행 전 자산은 비공개+서명URL, 발행 후 공개 CDN 경로. 인쇄용 PDF·원본 PNG는 별도 보관.

**기존 래스터 함정 계승**(mtspace-design-studio 스킬): onclone CSS 무시→CSS 변수 인라인 무력화, 가장자리 띠→cleanCanvasEdges(ref offset≥10), addColorStop→transform 제거, 25MP 초과→세로 분할 ZIP. html2canvas 폴백 사용 시 동일 대응. 서버 렌더(Satori/Playwright)는 이 함정 대부분이 사라지나, **결과는 픽셀 검증**(가장자리·해상도·폰트) 절차 유지.

### 14.5 검수·발행 게이트
- 텍스트(상세·블로그): KB 사실검증 결과 표시 + 사람 승인 → 발행. 미검수 자동발행 금지.
- 이미지: 미리보기·가장자리/해상도 확인 → 승인 → 자사몰/채널 발행.
- 모든 발행은 `audit_log`. 제품 프로파일 변경 시 영향 자산을 "재생성 필요"로 표시.

### 14.6 포팅 계획 (기존 HTML → 자사몰)
1. `MTSPACE_DESIGN_STUDIO.html`의 4개 캔버스 마크업·CSS·브랜드 토큰을 React 컴포넌트로 이식(치수·스케일 보존).
2. 입력폼 → 상품 등록 폼 필드로 통합(§14.2 매핑).
3. 블로그·키워드·KB 로직을 `content_draft`·`kb_entry`·`keyword`로 데이터화.
4. 래스터 경로를 서버 렌더(Satori/Playwright)로 1차 구현, html2canvas는 관리자 수동 폴백.
5. 자산을 `product_asset`로 연결·버전관리, 외부채널 내보내기 연결.

### 14.7 인스타그램 카드뉴스 엔진 (v1.3)

기존 `MTSPACE_instagram_cardnews.html`(단일 HTML, html2canvas)을 자사몰 카드뉴스 엔진으로 흡수한다. 레퍼런스: `CARDNEWS_TECH_DOCS.md` + `mtspace-cardnews-builder` 스킬 + `mtspace-coffee-brand`(24 SKU 컬러 진실 출처).

**모드(토글)**
- `simple`: 1080×1080 단일/소수 페이지(빠른 제작). v1.2 카드뉴스를 이 모드로 흡수.
- `narrative`: 1080×1350(또는 1:1), **Hook→Context→Detail→Experience→CTA 5장**, 역할별 3레이아웃(A/B/C, 15종). 관리자에서 슬라이드별 레이아웃 전환.

**데이터 소스 — 자사몰 DB 단일소스**
- 기존 라이브 `mtspace.coffee/products.json` 페치를 **자사몰 product 레코드 조회로 대체**(단일소스 원칙). 베이크된 스냅샷·CORS 의존 제거.
- 시그널 컬러는 `product.key_color`(24 SKU 실측 시드). 기존 35개 SKU 정규식 매칭은 **마이그레이션 시 key_color 시드 산출용으로만** 사용하고, 런타임은 필드 값을 신뢰.
- 신규 제품 key_color 미지정 시 폴백 = Brand Blue `#0076BA`(관리자에 "컬러 미지정" 경고).

**색상·텍스트 규칙(계승)**
- 페이지 색: 홀수=`color1`(Ink Black `#1A1A1A`), 짝수=`color2`(제품 key_color 또는 브랜드 컬러).
- 밝은 시그널(rec.709 luminance>0.6, 6종) 위에는 **검정 텍스트 자동**(`signal-light`). 신규 밝은 컬러도 동일 판정.

**자동주입(`data-fill`/`data-tn`)**
- `title`→`{shortTitle}.`(CTX), `description`→설명 발췌(CTX), `farm`→`farmName(product)`(CTX/CTA), `process`→가공(CTX), `now-farm`→`지금, {농장명}.`(CTA), `data-tn 0~4`→`flavor_notes`(DETAIL, 최대 5).
- `farmName()`(블렌드=한글부분, 싱글오리진=국가 prefix 제거+가공 suffix strip)·`parseTastingNotes()` 로직 이식.
- **사용자 수정 보호**: 편집된 요소는 `dirty` 표시 → 자동주입이 덮어쓰지 않음.
- 의도적 고정 슬롯(브랜드 메시지): HOOK 헤드/eyebrow, CTX-c 인용, EXPERIENCE 전체, CTA verb/tag.

**폰트 시스템(계승)**
- `--fs-head`/`--fs-body` CSS 변수, 기본 0.8/0.7, 범위 0.5~2.0(10% 스텝). 폰트 크기는 **cqi 단위**(컨테이너 비율 보존, px 금지).
- 브랜드 chrome(`.wm` 워드마크·`.wm .tagline`·`.pager`·`.role-tag`)은 슬라이더 무관 **리터럴 `*0.7` 고정**, 폰트는 항상 Helvetica Neue.
- 폰트 패밀리 4종(sans/myungjo/gothic/times) — 본문에만, 워드마크 제외.

**브랜드 인식(멀티 스토어프론트)**
- 현재 스토어프론트(놈코어/엠티스페이스)에 맞는 워드마크·토큰·CTA 핸들(@normcore_coffee / @mtspacecoffee)·언어를 주입. 템플릿은 공유하되 브랜드 토큰만 분기.

**렌더링·출력**
- 포팅: 단일 HTML의 `<template>`·CSS(cqi)·테마 로직을 **React 컴포넌트**로 이식. 서버 렌더(Playwright 권장 — 5장 다중·정밀)로 PNG/JPG 생성, html2canvas는 관리자 수동 폴백.
- 출력 크기: narrative 1080×1350(또는 1:1), simple 1080×1080. 파일명 `{brand}-{nn}-{role}-{layout}[-{handle}].{ext}`.
- 결과는 `product_asset(type='cardnews', storefront_id, status)`로 연결·버전관리. 다중 페이지는 페이지별 asset 또는 묶음.

**"단일 HTML/백엔드 금지" 원칙 처리**
- 기존 도구의 1순위 원칙이었으나, **자사몰 통합 시 폐기**(서버 렌더·DB가 전제). 단, 디자인·브랜드 규칙(5장 구조·시그널 컬러·자동주입·cqi·워드마크 불가침)은 그대로 계승. 기존 단일 HTML은 **현장 빠른 수동 도구로 병행** 유지 가능.

**알려진 제약 대응(계승)**
- 풍미노트 없는 제품(예: Normcore Standard) → DETAIL 자동주입 생략, 수동 입력. localStorage 자동저장 부재 → 자사몰은 초안 DB 저장으로 해소. 신규 SKU 컬러 폴백 → key_color 입력 유도.

- **브랜드/권한**: 스토어프론트별 FAQ 셋, 도매·세금계산서 FAQ는 승인 B2B만(RLS·필터, §2.4).

### 15.2 동적 변수(단일소스 주입)
- 답변 본문의 **신선도·로스팅(월·화)/출고 일정·배송비·배송 소요일** 등은 **변수 토큰**으로 작성 → 렌더 시 단일소스(설정/상품 데이터)에서 주입. 값 변경 시 FAQ가 자동 갱신(하드코딩 금지).
- 예: `{{roast_days}}`(월·화), `{{ship_days}}`(화·수), `{{free_ship_threshold}}` 등.

### 15.3 구조화 데이터(FAQPage)
- `/faq` 및 상품/정책 페이지의 FAQ 블록에서 **FAQPage JSON-LD** 자동 출력 → 검색·AI 인용. 자연어·명확 질문/답변(AIEO).

### 15.4 자동화·피드백(P1)
- 연락처 폼·반복 질문 로그에서 FAQ 후보 추천, 제품/지식베이스 기반 답변 초안(LLM) → **검수 후 게시**(미검수 자동게시 금지).
- "도움이 됐나요?" 피드백(up/down), 미해결 시 연락처 폼 연결.

### 15.5 관리자
- faq CRUD, 카테고리·정렬·게시, 변수 토큰 미리보기, 브랜드/상품 연결, audit_log.
